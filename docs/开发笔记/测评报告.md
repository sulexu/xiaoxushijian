### 2.1 一处低危：笔记里的 `javascript:` 链接

**位置**：`static/app.js` `mdInline()`（原第 6012 行）

```js
.replace(/\[([^\]]+)\]\(([^)\s]+)\)/g, '<a href="$2" target="_blank" rel="noopener">$1</a>')
```

`$2` 直接进 `href`，**没有协议校验**。`esc()` 挡不住这个：
`javascript:alert(1)` 里一个需要转义的字符都没有，转完还是原样，
于是笔记里写 `[点我](javascript:...)` 会生成一个**可点的可执行锚点**。

**为什么算低危**：笔记是你自己写的，且需要手动点击。
**为什么仍要修**：笔记是 Markdown 文件，**能手工编辑、能导入**，
不该靠「只有我自己写」兜底。

### 2.2 一个**真 bug**：源码里含裸 NUL 字节

**位置**：`static/app.js` 第 5867、5892 行，字节偏移 315845 / 317142

```js
const key = kind + "<NUL>" + q;        // 字节序列 22 00 22
if (x.startsWith(k + "<NUL>")) ...
```

**现象**：这两个字符串字面量里嵌的是**裸的 0x00 字节**，不是转义序列 `\0`。
作者本意几乎肯定是 `"\0"`（反斜杠 + 0，两个字符）—— **语义等价**
（都是 U+0000 分隔符），但后果是：

- 文件**不是合法 UTF-8 文本**，含 2 个 NUL
- 于是 `grep` 认得出它、**但任何按文本处理的工具（含本项目的编辑工具链）
  会把它判成二进制文件**，拒绝编辑
- 实测：本次测评第一次尝试修改 `app.js` 时就被拦下
  （`Error: cannot edit ...: binary file`）

**为什么值得修**：它不是"能跑就行"的问题 —— 它让**改这个文件本身**变难，
而这正是 `项目交接.md` B1 / H 类那两课（"看不见全貌"导致的慢性病）的同一族。
已修：字节 `22 00 22` → `22 5C 30 22`（即 `"\0"`），**文件 +2 字节，语义不变**。

## 3. 严重发现：两个主测试套件曾静默失效

### 3.1 现象

```
笔记    79 项   ✅ 通过
加密    22 项   ✅ 通过
迁移    25 项   ✅ 通过
后端主 193 项   ❌ 无法启动
升级    27 项   ❌ 无法启动
────────────────────────────────
可跑 126 / 346；前端 337 项未测
```

### 3.2 根因

数据 **2026-09-19 搬出了工作目录**，现在在 `D:\小煦拾简\数据\`
（`%APPDATA%\小煦拾简\数据位置.txt` 里写着），但这两个脚本还在按**目录结构**推算位置：

| 脚本 | 原代码 | 实际后果 |
|---|---|---|
| `_自测.py:19` | `ROOT = os.path.dirname(BASE)` | 去 `D:\个人信息统计` 拷三本 Excel → `FileNotFoundError` → **栈直接退出**，193 项一项没跑 |
| `_升级校验.py:18` | 同样 `os.path.dirname(os.path.dirname(...))` | 打印「找不到真实数据库」→ 27 项一项没验 |

而 `_自测报告.txt` 停在 **2026-09-19 00:13**（迁移之前），**报告本身没更新过**.

### 3.3 为什么这条最严重

按 `用户需求和决策习惯.md` §0：「**你说要跑测试，他会认真看结果**。
测试是他判断「能不能信」的依据。」

现在最重的那个 193 项套件**不是变红，是根本跑不起来** ——
而且外面看起来和"没跑"一模一样。这属于 §5.3 里你最不能接受的那一类：
**它不吭声。**

⚠ 更隐蔽的一点：`_自测_迁移.py` 的最后一步**真的把源库删掉**
（实测输出 `[OK] ★★ 说了删，这次真的删掉了`），
所以按老顺序跑时，迁移套件会顺手清场，更不容易发现另一个套件已经挂了。

### 3.4 修法（分两层，第二层是修第一层时才暴露出来的）

**第一层 —— 脚本自己找不到数据目录：**

两个脚本都改成**读 `%APPDATA%\小煦拾简\数据位置.txt`** ——
那才是「数据在哪」的权威来源，`electron/main.js` 的 `ROOT_CFG` 用的也是它。
保留工作目录作为回退，并且：

- 两个候选都不像数据目录时，**打印清楚找了哪两个地方**，而不是抛栈
- 缺哪个源文件就列哪个，并指出该去核对哪个配置文件
- `_自测.py` 的 `main()` 返回值改成退出码（原来裸调用，`return 1` 无效）

**第二层 —— 修完第一层，193 项能跑了，但露出 3 项新失败：**

```
[FAIL] 2.4.5 日历自测 崩了：OperationalError('unable to open database file')
[FAIL] 2.4.1 时钟/回忆书自测 崩了：OperationalError('unable to open database file')
[FAIL] 2.3.8 背景默认值自测 崩了：OperationalError('unable to open database file')
```

**根因**：这三处子自测走的是**进程内 `importlib.import_module("server")`**
（`_自测.py` 第 624 / 685 / 742 行），而 `server.py:87` 是：

```python
DATA_ROOT = os.environ.get("STATS_ROOT") or _find_data_root(...)
```

**`DATA_ROOT` 在 import 那一刻就定死了**，之后再改环境变量不回头生效。
而设置 `os.environ["STATS_ROOT"] = COPY` 的那行原来在**文件末尾**（原第 884 行）——
也就是说这三处 import 全都发生在设环境变量**之前**，拿到的是**默认数据目录**。

**为什么以前碰巧不炸**：默认数据目录以前是工作目录，那儿的库文件存在；
数据搬家后默认位置解析到了新目录，虽然库在，但这三处走的是内置 `store`
（副本化的连接参数），路径对不上就开不了库。

**修法**：把 `os.environ["STATS_ROOT"] = COPY` + 清 `sys.modules` 缓存
**提到文件开头**（第一次 import server 之前），并在那里写明
「必须在第一次 import 之前，因为 DATA_ROOT 是 import 时定死的」。

> ⚠ 这一条本身是个教训：**修好一层，才会看见下一层。**
> 如果只停在第一层（能跑起来了），这三项会一直是红的，而原因和第一层完全不同。

## 4. 中等发现：`semester_switch` 可能报「成功」但没落盘

**位置**：`server.py:360 _save_data_config()` 与 `server.py:392 semester_switch()`

原代码：

```python
def _save_data_config():
    try:
        cfg = _load_json(DATA_CONFIG, {})
        cfg["semester"] = SEMESTER
        _save_json(DATA_CONFIG, cfg)
    except Exception:
        pass                    # ← 什么都不说
```

```python
with _write_lock:
    old = BILL
    SEMESTER, BILL = name, f
    _save_data_config()         # ← 不看返回值
...
return True, "已切到「%s」" % name   # ← 无条件说成功
```

**后果**：落盘失败时（磁盘满 / 配置文件被杀毒锁住），
**界面说「已切到 X」，而重启后回到旧学期** —— 静默说反话。

**为什么这条值得修**：全库共 **30 处**静默吞异常，绝大多数是合理的
（例如备份失败绝不能挡住正常保存，`server.py:929` 的注释写明了这个取舍）。
但这一处落在**改状态**的路径上，属于"说了话就要算数"的那一类。

**修法**：`_save_data_config()` 返回 `True/False` 并 `log_error` 记一笔；
`semester_switch()` 失败时**把内存状态退回去**，并说清
「数据文件没有动，还是原来的学期」。

**核实过调用方**：`_save_data_config()` 全库只有 1 个真实调用点（就是这里），
所以改返回值不会波及其他路径。
